# 首页与播放页加载延迟修复设计

日期：2026-10-08。基线：当前工作区 `1.0.0+369`。本文为设计，不代表已实施或已重新进行真机验证；不修改运行代码、版本、安装包或既有留档。

## 1. 推荐结论与实施边界

保留五页渐进预热、常驻数据 worker、300ms 首页两端点切换及播放页 620ms 入场/460ms 退出动效。调整为：**轻量界面及时显示；数据与资源分别准备；冷计算不由点击和滑动触发；已准备的背景与基础控件允许随播放 route 入场。**

旧规则“入场只允许路由、Hero、封面”与“控件和背景及时出现”存在直接冲突：严格保留旧规则，就必然有至少约 620ms 的显示等待。推荐按本次延迟修复目标调整规则，限制冷计算而不限制已准备内容的显示。不通过缩短动效、关闭流体/模糊/逐字效果掩盖问题。

不提前 push 隐藏播放 route，不同时挂载第二套 Hero，不预建整张歌词列表，不全面扩大图片缓存。歌词绘制算法、播放逻辑、用户设置与数据保持现有行为。后台不运行新的预热，资源失效和系统回收后允许重新准备。

## 2. 已确认的等待链

| 问题 | 当前生产路径 | 修复方向 |
| --- | --- | --- |
| 除乐库外首页首次进入很慢 | `mobile_shell.dart` 给所有页面同一个 `prepareLibraryPresentation()`；歌单、设置也等待歌手/专辑、拼音、排序键、搜索全部完成 | 按页面声明实际依赖，解除全局准备门槛 |
| 冷目标页空白 | `HomeTabViewport` 未 prepared 时只显示 `SizedBox.expand`；`_GroupTab` 无上次视图或全局数据未就绪时也返回空白 | 五页稳定轻量外壳先就绪，有缓存显示缓存，无缓存显示明确占位 |
| 点击目标不能及时获得准备机会 | 单串行预热循环先选目标再 await 全库准备，完成后仍准备旧目标；所有页挂载为 maintenance，过渡期间禁止执行 | 独立任务、目标变更时重新选择并提升优先级 |
| 播放页控件迟到 | route 完成后 `_preparePlaybackChrome()` 才排队，先挂全部控件，再挂背景 | 基础控件随 route 显示，重资源独立准备 |
| 背景更晚出现 | 背景晚于控件挂载；流体组件内部再等待 shader 与调色板 | Mini Player 出现时准备当前曲目资源，背景显示不依赖控件就绪 |
| 背景出现时重复初始化前景 | 外层从 `ColoredBox(child: scaffold)` 换为 `PlaybackBackground(child: scaffold)` | 固定父节点和前景位置，只更新背景槽 |
| 调度优先级仍可能无效 | 全局只允许一个 idle lease；封面预解码及流体准备持有 lease 跨越异步等待；高优先级不能抢占已授出的 lease | 许可约束短主线程工作，异步资源任务独立限流 |

Flutter Element 更新要求同一位置的 widget 类型与 key 匹配，当前外层类型变化会替换其子树。稳定父节点可以消除这一确定的重复挂载；不能据此断言它解释了所有 50–60ms 尖峰。[官方 canUpdate 文档](https://api.flutter.dev/flutter/widgets/Widget/canUpdate.html)。

369 已有真机 Profile：预热完成后的 18 次主页切换最大 Build 16.305ms，未出现 >16.67ms 帧；播放页进出最大 Build 60.354ms，仍有超预算。主切页测量前等待了启动空闲，立即拖动场景主要验证帧耗时，未充分测量冷目标内容显示延迟。旧数据不能证明本次问题已解决。证据保持原样：`docs/android_369_idle_home_playback_preparation.md`、`F:/AGENT/1/test-artifacts/home-prewarm-369/`。

## 3. 首页修复

### 3.1 外壳与内容分开

启动首屏之后，先分帧挂载五个轻量外壳，保留原高度、列表区域和滚动位置。每个外壳独立持有最近可用的展示快照、数据准备状态和首屏封面状态。页面可见不再取决于一个全库 `libraryPresentationReady`。

| 页面 | 首屏真正需要 | 不作为显示门槛 |
| --- | --- | --- |
| 乐库 | 当前歌曲展示快照、首屏行数据 | 全部搜索索引、隐藏页面封面 |
| 歌单 | 歌单列表和现有展示信息 | 全曲库歌手/专辑分组、拼音搜索 |
| 歌手 | 歌手分组与该页排序/代表歌曲展示结果 | 专辑页挂载、全曲库搜索索引 |
| 专辑 | 专辑分组与该页排序/代表歌曲展示结果 | 歌手页挂载、全曲库搜索索引 |
| 设置 | 设置 provider 的现有值与首屏控件 | 曲库分组、拼音、封面解码 |

设置详情继续按需加载。真实空曲库和“尚未准备”的状态必须区分；准备失败可以重试，不停留在永久空白。已有内容在刷新期间保持显示，应用新快照时保留稳定 key、滚动锚点与选择状态。

无有效数据缓存的首次启动，先显示外壳与占位，后台尽快生成真实内容；不能保证尚未读取的数据在下一帧完整出现。只有准备完成的内容，才能实现切页主体主要做位移与合成。标题、导航选中状态等必要更新仍存在。

### 3.2 拆开 worker 的产出

将当前一包返回的 `PreparedLibraryMetadata` 拆成可独立发布的结果：

1. 对现有歌曲元数据先完成歌手/专辑分组、计数，避免每首先算全套拼音才推进分组。
2. 生成当前目标页需要的唯一分组名称排序键、列表展示结果和代表歌曲索引；发布该页即可使用的快照。
3. 在后续空闲时补齐所有歌曲标题/歌手/专辑的拼音、首字母、混合字符键和搜索索引。

保留排序语义：按拼音排序的页面不能把未经转换的顺序当成最终结果。优先沿用有效缓存顺序；无缓存时保持占位或明确的暂态列表，完整排序在安全时机一次应用，避免滑动期间反复跳位。拼音字典第一次初始化仍可能影响首个拼音排序结果；解除它对歌单、设置及无需该排序页面的影响，不宣称字典初始化免费。

输入组装和主线程结果发布都分批、计时。worker 返回紧凑索引及展示数据，避免主线程在一次发布里重建全部 `Map<String, List<Song>>`、搜索对象和所有页面。最终快照提交应是短操作，各页独立通知；getter/build 不回退到同步全库分组或拼音计算。

每次任务带曲库修订、分隔规则、排序设置和请求代际。旧结果不得覆盖新状态。当前 worker 的同步大任务不能靠取消 Future 抢占；应分块处理并在块之间接收新目标、取消或暂停请求。正在执行的字典初始化不能强行保证可中断。启动元数据修正连续发生时合并请求，不因每个细小修订反复清空可用视图。

### 3.3 持久展示缓存作为第二阶段增强

先复用现有元数据缓存和歌曲快照，不引入新的数据库框架。如果冷启动实测仍由分组/拼音初始化主导，再增加有界的分组展示缓存与排序键缓存。缓存包含稳定歌曲标识、分组/代表索引、schema 版本、元数据指纹、分隔与排序规则；不能用每次进程重置的运行时 revision 判断跨启动有效性。

缓存读写和校验在后台完成，原子提交。确认快照兼容后用于展示；点击操作重新解析当前真实歌曲状态，不能依赖陈旧列表索引。损坏、规则变化或缺失时正常重建，不写回覆盖正式曲库/歌单文件。

## 4. 播放页修复

### 4.1 固定前景结构

整段生命周期保持 `Stack → 背景槽 + 前景 Scaffold`。`Scaffold`、`NowPlayingImmersiveLayout`、封面 Hero 与控制区保持同一父节点位置和稳定身份。背景槽可切换同曲目的静态呈现与实际效果，不能再次包住/搬迁前景。

实施前用 mount/dispose 计数复现背景 ready 时前景二次挂载；修复后背景到位、切换样式和恢复前台均不应再次初始化前景 State。保留现有封面几何，基础控件出现不改变封面 Y 坐标与尺寸。

### 4.2 基础控件及时显示

从首次 route 构建就显示已知歌曲标题、歌手、进度槽、播放/暂停、上一首/下一首及必要导航。控件只读当前已有状态、绑定现有播放命令，不读取文件、不计算全库收藏状态、不初始化歌词列表。它们跟随原入场动画显示和命中测试规则，无须等待 620ms 完成后的 idle lease。

详情、队列、音效等按钮可立即显示，重内容在实际打开对应面板时准备。完整歌词继续独立惰性挂载；不要因改善普通播放页而首次入场就创建歌词列表、排版全部歌词。字体/图标和基础控件首建成本若仍超预算，应先通过 CPU/Timeline 定位，再进行针对性预热，不预先复制整张 route。

### 4.3 Mini Player 准备当前歌曲资源

Mini Player 有歌曲时，在低优先级空闲任务中准备：按播放页真实布局和 DPR 确定的目标尺寸封面、当前背景所需调色板、选中的自定义背景或封面背景首个呈现资源。尺寸推导与实际播放页使用同一规则，横竖屏/分栏/大字体变化使缓存失效，不只按固定最大封面尺寸解码。

常驻 shader program 在合适空闲时预加载；每页 shader 实例、Ticker、FFT 订阅只由可见背景持有。Mini 不驱动隐藏背景动画，也不把 UI/shader 对象放进计算 isolate。已准备的流体资源可在入场期间绘制稳定相位，动画节拍按原过渡保护策略启动；用户仍获得及时的背景呈现。

缓存键包括歌曲身份、封面代际、背景样式和资源参数。继续限制当前大封面保留数量及字节预算，背景快照有界；快速切歌仅最新代际能提交。`precacheImage` 完成不保证永久缓存或 GPU 首次上传已经完成，不能用资源 Future 完成替代首帧 Raster 验证。[官方 precacheImage 文档](https://api.flutter.dev/flutter/widgets/precacheImage.html)。

点击进入后，已缓存资源直接使用；缺失资源提升为可见请求，不排在五页预热后。封面先复用同曲目的 Mini 图像/当前有效图像，目标尺寸图像异步接替；背景先呈现同曲目已有静态结果，重效果准备独立推进。无缓存时保留明确基础背景并记录最终背景到位时间，不能把这个基础背景计作最终效果已完成。

控件显示、背景显示、重效果运行三个条件独立。解除“控件 → 背景挂载 → 背景资源准备”的串行链。前后台恢复另行测试，现有玻璃恢复延迟不是全部控件首次出现的原因，不盲目删除恢复保护。

## 5. 调度改造

拆开短主线程准备/提交许可与异步资源并发控制。主线程许可不跨越文件读取、worker 回复、图片解码和 shader asset 等待：获取许可启动必要操作后释放；结果到达再按代际与可见性申请短提交。异步解码和后台计算仍限流，避免把全局串行等待改成无限并发。

优先次序为当前可见资源、当前目标页内容、当前歌曲的 Mini 预备资源、其余主页首屏、相邻曲目维护。纯预热不阻塞已可见界面的短更新；当前目标变化时重新排序并合并重复任务。已执行的异步解码不可假定能够抢占取消，应限制在途数量、丢弃过期提交并记录阻塞时间。

每个主线程批次以耗时预算为主，初始建议 2–3ms 后让出执行机会，结合真机调整；“每 128 首”作为数量上限之一，不能作为耗时保证。`Future.delayed(Duration.zero)` 只是让出事件循环，不保证自动落到下一帧或不存在长任务。接到手势后停止新增重主线程批次和隐藏页挂载。

route 保护改为有所有者的开始/完成/取消票据，超时仅兜底。不能为让控件提前出现直接调用全局 `endPhase`，误解除其他手势保护。已准备的可见界面短更新无需通过纯预热队列；重任务继续受保护。回到首页后，依据实际退出完成信号恢复目标页准备，避免沿用 620ms 保守等待遮住 460ms 退出后的时间。

## 6. 各组件后续优化

| 组件 | 优化 | 必须保留/验证 |
| --- | --- | --- |
| 顶层播放页 | 将大 selector 与 Settings/Theme 全量 watch 缩为分区依赖；独立封面、标题、进度、控制、背景 widgets | 收藏/播放状态改变不重建整页；曲目和主题变化正确更新 |
| 时间文字与进度 | 时间文字通常按秒变化；Slider、拖动预览保持及时更新 | 拖动预览立即响应，不给歌词媒体时钟降采样 |
| 收藏与模式按钮 | 收藏集合按修订预归一化为 Set，叶子选择 bool/枚举 | 收藏同步、路径规范化与切歌一致 |
| 封面 | 按当前曲目维护稳定监听；复用同一目标尺寸图像 | 快速切歌不显示旧封面，Hero/尺寸不跳动 |
| 背景与玻璃 | 复用调色板、program、固定滤镜；仅背景槽更新 | 保留既有视觉模型；测 Raster、首效果帧与内存 |
| 歌词 | 空闲预热焦点及少量邻行的现有字形缓存；首次列表建构单独跟踪 | 不更改逐字运动、焦点、手势与排版算法；UI 文本排版不强塞 isolate |

优先改变更新范围，不以大量 `RepaintBoundary` 替代 build/layout 优化。按状态变化拆成独立 widget、局部更新是 Flutter 官方建议；不能只把大 build 拆成几个函数就认为重建被隔离。[官方性能建议](https://docs.flutter.dev/perf/best-practices)。

## 7. 实施顺序与验收

1. **先测可见延迟与等待链。** 为导航请求、目标外壳首帧、真实首屏内容、首屏封面、基础控件、实际背景首帧/首动效帧、任务排队/开始/结束添加关联标记，同时记录 mount/dispose 与 FrameTiming。用 CPU/Timeline 区分 route/Hero、源页依赖更新、控件和背景工作。
2. **先解除结构性门槛。** 首页按依赖准备，冷页有稳定外壳；播放页固定背景/前景树，基础控件不等待 route 结束，背景不等待控件。用故意延迟 worker/解码的测试证明显示不再受无关任务阻塞。
3. **再改调度与资源准备。** 释放异步等待期间的主线程许可，目标页提升优先级，当前曲目封面/背景预备独立运行；覆盖任务过期、失败、销毁、暂停/恢复以及持续切页。
4. **再拆数据与组件。** worker 分阶段产出、短提交、各页快照；控制区局部更新。仅实测仍需要时增加持久分组/排序缓存，歌词优化最后独立验证。

真机矩阵：每种至少多次重复，记录 P50/P95、最大值及失败情况；有需要时扩至 20 次用于初步 P95 比较。旧 95 首实际曲目数据用于可比基线，另以隔离实验数据验证大曲库，不改正式曲库。

| 场景 | 检查 |
| --- | --- |
| 冷启动后首页出现即切页；另测 +100/+300/+1000ms | 歌单、设置不等待分组；歌手/专辑有反馈，最终真实内容到位；不能预先空闲 6 秒 |
| 连续跨页点击、反向滑动、预热中操作 | 最新目标优先，外壳不空白、内容不跳位，手势中无全库主线程计算 |
| 启动后立即点 Mini；预热未完成即点；资源已准备再点 | 封面/基础控件/真实背景各自的首次呈现时间，620ms 动画内是否已有基础内容 |
| 快速切歌后进入/退出；主题或封面代际变化 | 无旧资源回写，无重复 Hero，无前景二次挂载 |
| 图片缓存淘汰、背景资源慢/失败、worker 慢/失败 | 可见内容仍响应，任务有限重试，不永久空白，不让异步等待垄断全局许可 |
| 前后台恢复、旋转、大字体、长时间使用 | 原恢复保护、封面几何、缓存失效、监听与内存上限 |

建议验收目标（设计目标，非实测结论）：外壳/操作反馈在下一可用帧，点击后 P95 ≤100ms；有效数据和资源缓存命中时，真实首页内容、基础播放控件与正确背景首次呈现 P95 ≤200ms，不等整段入场结束。无有效缓存时记录实际完成时间及来源，先保证反馈，不承诺未知存储/曲库规模下最终效果统一 ≤200ms。重复入场与背景 ready 不重复初始化前景；设置/歌单不受故意延迟的分组任务影响。

同时要求同设备同设置的 Build/Raster P95 不劣于基线，报告最大值与超预算帧；不能只提高显示速度而放大 route 尖峰。依据实际 vsync 确定预算，现有设备采样约 60Hz，应按约 16.67ms 评估；120Hz 若确实生效则另外按约 8.33ms 测量。待效果和帧时序均验证后，再按 AGENTS 流程递增软件构建、顺序测试/分析/ARM64 Release、隔离 Profile 与正式覆盖升级留档。

本轮交付限于方案。未重新连接设备、运行软件测试或生成 APK，369 历史证据与产物保持不变。
