```text

先完整阅读规划和诊断，再检查仓库规则、当前 SDK、Git 工作区和相关实现。诊断使用过 Flutter 3.44.9、vivo V2352A / Android 15、Impeller/Vulkan、约 60Hz，但不要假定现在状态完全一致。规划中的数值是初始工程目标，诊断的小样本不是所有设备的保证。

用户最明显的问题是首次进入播放页或切歌后进入卡顿。已有证据表明：组件挂载/更新导致约 28–35ms 的 build 峰值；背景模糊与面板毛玻璃有可分离的 raster 成本。同时关闭这两类模糊，进入 raster P95 曾从约 18.9ms 降至 10.6ms，但 build 峰值仍在。请分别解决这两部分，不用延长进入动画掩盖问题。

【工作方式】
1. 保护所有既有未提交修改。不要 reset、强制 checkout、覆盖别人的编辑。需要临时诊断代码时记录精确备份，恢复前验证没有并发改动。
2. 先重现与记录基线，再按阶段连续实施。例行实现、可逆编辑和适当测试自主推进；只有真实缺失信息、设备授权或破坏性操作阻塞时询问。
3. 只在本项目范围工作。不要未经请求升级 Flutter、引入重型插件、重构音频引擎、改权限或清理用户文件。复用已有色板、缓存、交互与生命周期设施。
4. 进展说明聚焦发现、数据和下一步。最终输出必须区分实现状态、实测结果和未测限制。

【先检查这些位置；名称/行号以现有代码为准】
- lib/mobile/mobile_shell.dart：_openNowPlaying、_GentleNowPlayingRoute、_NowPlayingPageState、封面准备协调器、毛玻璃面板和歌词背景。

【产品要求】
1. 在现有背景入口新增可选“流体色彩”，默认保持用户原背景选择和旧参数。已有图片/封面背景继续可用。
2. 跟随封面取 3–5 个稳定代表色；约 4 个缓慢漂移的柔和色团加少量坐标扭曲。高档复杂度只在测试通过后增加。效果柔和、亮度稳定，不影响歌词阅读。
3. 首版仅播放页共用背景，不扩展到主页。不做真实流体、FFT/节拍、触摸搅动、视频、WebView 或多遍反馈模拟。
4. 首帧立即显示已有封面、标题和播放控制；资源未就绪用静态渐变。路由进入/返回期间冻结流动，稳定后启动；不能固定等待一个时长就认定路由完成。
5. 暂停播放后平滑停在当前相位；后台、锁屏、不可见时停止持续工作。返回手势取消后可恢复。减少动态效果时保持静态。
6. 切歌保持运动连续，在同一 shader 内插值色板，避免两层全屏动态背景交叉淡入。连续切歌从当前显示颜色继续，过期结果不能覆盖最新歌曲。
7. 流体模式不叠加现有全屏高斯模糊；默认将面板实时毛玻璃换为适合该模式的半透明填充与边框。旧模式的处理独立验证，不全局粗暴关闭效果。

【技术要求】
- 使用 FragmentProgram/FragmentShader + Paint.shader + CustomPainter 直接绘制单个背景矩形；shader 声明在 flutter.shaders。
- 使用 CustomPainter(repaint: Listenable) 更新，避免每帧页面 setState、Provider 全局通知或歌词列表 rebuild。
- 复用 FragmentProgram 与各自拥有的 FragmentShader，正确处理 dispose、尺寸变化、uniform 索引、预乘透明度和长期时间精度。
- 不把 RepaintBoundary 当作动态内容自动缓存，不把 allowSnapshotting=true 当作 Cupertino 路由已生成快照。核查当前 SDK 的真实过渡实现，修正错误注释。
- 从已有小图取色；需要新采样时从 32×32/64×64 开始。按测量决定是否使用 worker isolate，仅传可传输数据，不跨 isolate 传 ui.Image。
- 色板缓存有界，初始上限可为 64 条；键包括封面版本。同请求合并，代际校验，处理图片替换、损坏、缺失、dispose 后异步完成。
- 每帧不解码、不提取色板、不重新加载 shader、不创建完整图片、不回读纹理、不写日志。
- 默认先尝试 30Hz 的背景参数更新，按 vsync 节流；高档最多请求 60Hz。前景保持自身刷新节奏。承认请求频率降低不等于实际 GPU 绘制频率降低，必须验证。
- 质量降低先简化算法/色团，再降低更新频率，最后静态。避免单帧触发反复升降；采用持续窗口和迟滞。系统省电能力必须实际核查，不虚构 API。
- 优先单遍 shader；只有实测表明像素成本过高才单独研究真正低分辨率 GPU 纹理。禁止用缩小 Widget 再放大或每帧 toImage/toByteData 冒充低成本渲染。
- 程序预加载不保证首次 GPU 使用无峰值；分别测准备和首次绘制，不假定 Offstage 会预热。

【交互和生命周期特别约束】
当前 InteractionPerformanceController 刻意没有 UI Listenable。用已有 route/lifecycle 事件和小范围控制器接口接入，不添加每帧全页广播或永久轮询。
waitForIdle 超时返回不代表真的空闲；必须重新检查。acquireIdleWork 需验证 isGranted、带 isStillNeeded，并在 finally 释放。不要持有租约等待网络，也不要让切歌任务无界排队。
不要改变 foreground_lifecycle.dart 对 inactive 与真正后台的区分；只让视觉策略在失焦时更保守，不能影响音频恢复。

【实施阶段】
P0：记录环境和 Git 状态，验证原问题，整理可靠 build/raster 基线及可重复采集方法。
P1：独立优化现有首帧负担与滤镜成本，缩小不必要挂载/主页更新，保持原进入时长先测。不要先删 Hero 或加长动画。
P2：实现固定色板的独立 shader 原型与静态回退，验证绘制和资源所有权。
P3：接入封面色板、切歌、路由、播放与生命周期；保持旧模式默认不变。
P4：完善设置、质量档位、减少动态效果和保守降级。
P5：完成真机矩阵、长时检查、release 冒烟、构建和最终报告。删除临时调试入口。
阶段可连续推进；不要完成原型就停止。若阶段性能不达标，继续定位并如实记录，不能静默降低验收要求。

【验证】
写必要的行为测试：设置迁移、色板版本失效、乱序切歌、取消任务、route/后台状态、ticker 停止、shader 失败回退、资源释放。避免只验证实现字符串或机械堆测试。
性能用 profile + FrameTiming，build/raster 分开；totalSpan 单独报告，不能把 totalSpan>16.67 直接当作掉帧。详细 Widget/CPU 追踪会增加开销，其数据用于归因，不混入普通性能排名。
按完整规划执行冷首次、热进入/返回、切歌立即进入、歌词滚动、拖动进度、后台恢复、连续播放和内存检查。同条件分批 A/B/A 或交替，记录刷新率/热状态；没测到的设备和场景写明未测。
以 B=1000/实际渲染刷新率为预算。目标：稳态 build P95≤0.5B、raster P95≤0.75B；各自超 B 比例争取<1%；进入/返回避免>50ms帧，并单独优化首帧。相对已优化静态版的整页 raster P95 增加争取≤min(3ms,0.2B)。这些是验收目标，不能承诺无条件达到，也不能从 P95 差推出纯 GPU 精确成本。
检查背景 tick 没有引发前景逐帧 build/layout；隐藏时没有持续背景任务；多次切歌/进退无单调资源增长。功能要覆盖旧模式和音频控制。
```
